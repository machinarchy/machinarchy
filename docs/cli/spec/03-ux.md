# 03 - User experience

> Transcripts are **specifications of text and behaviour**, not recordings: nothing here was run. Host names, IDs and fingerprints are made up. `$` lines are typed by the user; everything else is output. Stderr and stdout are not distinguished in transcripts unless it matters. Symbols and colour follow `07-brand.md`; `--plain` output is shown in section 12; tab completion in section 11.

## 1. Home screen

Bare `machinarchy` (also `machinarchy -o json`). It never prompts and never takes longer than the three requests it makes (`02-commands.md` 3.1); each has a 3 s budget on this screen and a failure degrades one line, not the whole screen.

**Not signed in**
```
Not signed in.
Another machine will not manage itself.

  Next:  machinarchy login
```
(The second line is lore; `--plain` removes it.)

**Signed in, everything fine**
```
machinarchy · company · production                          maxim (owner)
Session ends in 21 h

Hosts      14 ready
Last runs  r-4k2p9x1a  uptime                      ✔ 14 ok            2 min ago
           r-8d1q0b7c  systemctl is-active nginx   ⚠ 11 ok, 3 failed  1 h ago

  Next:  machinarchy run --on all -- uptime
```

**Signed in, attention needed** (the suggested next step is always the most urgent one)
```
machinarchy · company · production                          maxim (owner)

Hosts      12 ready · 1 waiting for key approval · 1 cannot connect
           web-14  waiting for key approval
           web-09  cannot connect
Last runs  none yet

  Next:  machinarchy hosts trust web-14
```

**Signed in but no hosts**
```
machinarchy · company · none                                maxim (owner)

You have no machines yet.

  Next:  machinarchy hosts add
```

**Server unreachable**
```
machinarchy · company (https://machinarchy.example.com)
✖ Cannot reach the server: connection refused.

  Next:  check the address, or switch server: machinarchy switch
```

**Session expired**
```
Your session on company expired at 09:14.

  Next:  machinarchy login
```

Priority of the suggestion: (1) not signed in or expired -> `login`; (2) host `key changed` -> `hosts show NAME`; (3) `waiting for key approval` -> `hosts trust`; (4) `cannot connect` -> `hosts show NAME`; (5) no hosts -> `hosts add`; (6) otherwise a run example using a real host tag if one exists.

The host counts use the readiness mapping in `02-commands.md` 3.8.1. A session's remaining time comes from `GET /api/v1/sessions`; a token's expiry is shown only if the server reports it (C-03).

Goal: install, sign in, first machine managed, first command run, in under five minutes. Install is a download of the release binary plus checksum check (README quick start, M6); `machinarchy --version` confirms it.

### 2.2 Agent path

An agent host is reached through an agent installed on the machine. The CLI can print the install command only when the controller publishes the agent connection details (C-07). Until then it prints the four values and where each comes from, and says so.

```
$ machinarchy hosts add db-01 --agent
[machinarchy-example-com · none] Add a machine reached by an agent

✔ Access "agent" found (agent).
✔ db-01 added. It stays "waiting for agent" until the agent starts.

One-time enrolment token (valid 1 hour, shown once):
  mae_9f3c...

On db-01, as an administrator, run:
  <the install command supplied by the server (C-07)>

Waiting for the agent to connect (Ctrl+C to stop waiting, the token stays valid) ...
✔ db-01 is ready (31 s).
Another operative reports for duty.

  Next:  machinarchy run --on db-01 --do runtime.info
```

If C-07 is not available:
```
This server does not publish its agent connection details, so the install command
cannot be written for you. The agent needs these four values (see the agent's README):
  NATS address        ask whoever runs the server
  NATS credentials    ask whoever runs the server
  Controller key      machinarchy hosts enroll db-01 --show-controller-key   (works today)
  Enrolment token     mae_9f3c...  (above)
```

Rules: the enrolment token is printed once, never logged, written to a file only with `--token-out FILE` (0600, no overwrite); re-running `hosts enroll db-01` issues a new token and does not revoke earlier unused ones; `hosts enroll db-01 --revoke-old` also revokes them (`DELETE /api/v1/agents/enrollment-tokens/{id}`, verified). An enrolment needs an owner session.

If the controller reports the agent gateway is not configured (HTTP 503 on `controller-key`), `hosts add --agent` stops before creating anything: "This server has no agent gateway. Use an SSH host, or ask the server owner to enable agents."

### 2.3 Timing budget

Targets used by the five-minute test (`09-acceptance-tests.md` A-01): install 60 s, login 30 s, `hosts add` 120 s including up to 90 s of waiting, first run 20 s, slack 70 s. Waiting messages always show elapsed time.

## 3. Login

### 3.1 Email and password
Covered in 2.1. Details:
- Password is read from a terminal without echo, or from stdin with `--password-stdin`. Never from a flag or an environment variable.
- Email or username: the prompt says "Email or username"; the API accepts either (`auth.LoginRequest`).
- Throttled: `Too many attempts. Try again in 40 s.` Wrong credentials: `Sign-in failed: email or password is not right.` followed by the command again.
- The server URL may omit the scheme; `https://` is assumed. `http://` to a non-loopback host is refused with `Use https://. For a trusted lab network add --insecure-http to this login`; the choice is saved per server and shown in `whoami`.

### 3.2 API token
```
$ machinarchy login https://machinarchy.example.com --with-token
API token: ········
Checking the token ...  ✔ Signed in to machinarchy-example-com as ci-deploy.
  Role: not reported by this server     Expires: unknown
  Next:  machinarchy hosts
```
In CI: `printf '%s' "$TOKEN" | machinarchy login https://machinarchy.example.com --with-token --no-input`, or simply set `MACHINARCHY_TOKEN` and `MACHINARCHY_SERVER` and never save anything. A token read from the environment is never written to disk.

The token is validated with `GET /api/v1/me` **before** it is saved. A rejected token: `Error: the server did not accept this token. It may be wrong, expired or revoked.` `Next: machinarchy login --with-token`. Role and expiry are shown only when the server reports them (C-03); the CLI never infers a role from a failed request.

### 3.3 Stay signed in
A device token is an ordinary API token (role operator, 90 days, name `device-<computer>-<date>`) created with the password session. It is offered once per login on a terminal, saved in the credential store, and listed by `tokens`. It is **not** the default for non-interactive logins. A device token cannot do owner actions; commands that need an owner say so and use the session if it is still valid, otherwise print `machinarchy login`.

### 3.4 Expired or revoked credentials
```
$ machinarchy hosts
Error: your session on machinarchy-example-com expired at 09:14.
Next:  machinarchy login
```
For a device token: `Error: the saved device token was revoked or has expired.` / `Next: machinarchy login`. A 403 is not reported as expiry: `Error: ci-deploy (reader) is not allowed to run commands.` / `Next: use a token with the operator role: machinarchy tokens create ...` (owner).

### 3.5 Logout
`machinarchy logout` ends the session on the server and removes the local copy; for a token it removes only the local copy and prints "The token is still valid until it expires or is revoked: machinarchy tokens revoke NAME". `--everywhere` ends all of the user's sessions (not tokens).

## 5. Confirmations and blast radius

Three tiers (`04-security.md` section 5):

| Tier | Used for | Interactive | Non-interactive |
|---|---|---|---|
| T1 | run, tag, enrol, create | `[y/N]`, default no | `--yes` |
| T2 | remove host/access/env/token, revoke agent, retire secret, **any state change in a protected env** | type the exact name | `--confirm NAME`; protected env: `--confirm-env ENV` |
| T3 | host-key trust, changed host key, sign-in | its own flow | trust: `--fingerprint`; never `--yes` |

A confirmation always repeats the **server, env, action and count**, because those are the things people get wrong:

```
[company · production]  Run on 14 hosts: web-[01-14]
  Command   systemctl restart nginx
  Hosts     14 of 14 in "production" (protected)
  Limits    60 s per host, 5 at a time
Type "production" to run it:
```
For an `--on all` run outside any env the confirmation says `All 37 hosts on this server` and asks to type `37`.

Preview rules: the exact program is printed with the argument list quoted (`'rm' '-rf' '/tmp/x'`), never as a shell string; up to 10 host names are listed and the rest compressed (`web-[01-14]`, `and 23 more`); the preview is bound to the submission by the controller's `targetsHash`; if the hosts changed between preview and submit the controller refuses (HTTP 409 `targets_changed`) and the CLI says "The set of hosts changed while you were deciding. Nothing ran. Run the command again to see the new set."

## 6. Host lifecycle and removal

A host's life, from the user's side:

`added -> checking -> waiting for key approval -> ready` (SSH)  
`added -> waiting for agent -> ready` (agent)  
`ready <-> cannot connect | key changed` (controller observations)  
`removed` (inventory only)

**Removal never combines four different things.** Each has its own command and its own confirmation, and none implies another:

| Thing | What it means | Command | Can the CLI do it? |
|---|---|---|---|
| Inventory removal | The controller stops managing the host and forgets it. | `hosts remove NAME` | Yes (`DELETE .../hosts/{id}`, refused while a run targets it) |
| Agent uninstall | The agent software is removed from the machine. | none | **No.** The CLI prints the instructions to run on the machine. |
| Credential revocation | The key or password Machinarchy used on the machine stops working there. | none on the machine; `access remove` / `admin secrets delete` only on the controller | Controller side only. Removing `authorized_keys` on the machine is the owner's job. |
| Identity revocation | The agent can no longer serve commands. | `hosts revoke-agent NAME` | Yes (`POST /api/v1/agents/{id}/revoke`), subject to C-09 |

```
$ machinarchy hosts remove web-01
[company · production]  Remove web-01 from Machinarchy
  This removes it from the inventory only. It does NOT:
    • uninstall the agent from the machine (it was installed on db-01 by you)
    • revoke the agent's identity          machinarchy hosts revoke-agent web-01
    • remove Machinarchy's SSH access      delete the key from web-01's authorized_keys yourself
    • delete access "deploy-key"           machinarchy access remove deploy-key (other hosts may use it)
Type "web-01" to remove it: web-01
Type "production" to confirm the environment: production
✔ web-01 removed from the inventory.
```
(The third and fourth lines appear only when they apply.) An agent host that is removed but not revoked keeps a valid identity; the output says so in plain words: "The agent on this machine can still connect to the controller until you revoke it."

Safe order for decommissioning a machine, printed by `hosts remove --help`: (1) `hosts revoke-agent`, (2) remove the host, (3) remove the credential on the machine, (4) uninstall the agent. The CLI does not enforce it.

## 7. Runs and grouped output

### 7.1 Flow
1. Resolve `--on` and the env scope; call the preview.
2. Print the blast-radius preview and confirm (section 5).
3. Submit with the preview hash. Print `Run r-xxxxxxxx`.
4. Wait (default) with progress; then print the grouped result and exit with the run's code.

### 7.2 Grouping algorithm (the contract the aggregator implements)
1. **Outcome classes**, in this order: `succeeded` (exit 0), `failed` (non-zero exit, or error before start), `timed out`, `cancelled`, `outcome unknown` (`Lost`, `Interrupted`), `still running`, `not started` (`Pending`).
2. Within a class, the **group key** is the exit code, the controller's error class (for example `unreachable`, `outcome_unknown`) and the normalised stdout and stderr. Hosts with the same key form one group.
3. **Normalisation** replaces, before comparing: ISO-8601 and syslog-style timestamps, `HH:MM:SS`, UUIDs, `pid=N` and `[N]` PIDs, `0x...` addresses, and trailing whitespace. It never masks other digits (version numbers must stay visible). Display uses the first host's original text.
4. **Order:** failed and unknown classes first, then succeeded, because that is what the reader acts on. Groups are ordered by size, largest first.
5. **Host lists** are compressed: `web-[01-12,14]`, split by common prefix and suffix; hosts that do not match a pattern are listed whole and the list is cut to the terminal width with `(+37 more)`. Full lists are always available: `machinarchy run ID --groups all -o json`.
6. **Group display cap:** 10 groups (`--groups N`), then `and 4 more groups, 11 hosts: machinarchy run r-... --groups all`.
7. **Sample text** per group: the first 5 lines and 300 characters, with `[… N more lines]`. Output is always sanitised (T8).
8. **Drift** among succeeded hosts: if the succeeded hosts split into several groups and at least one group has two or more hosts, the smaller groups are called out, `⚠ 3 hosts printed something different from the other 11`. If every group has exactly one host (time-dependent output such as `uptime`), the CLI says `every host printed something different (normal for time-dependent output)` and shows no warning.
9. **Progress** on a terminal: one line redrawn at most twice a second, `████████░░░░ 120/200  ✔ 112  ✖ 3  ● 85 running`. When stdout is not a terminal, or `--plain`: a plain line every 10 seconds and at each 10 %, no redraw. Progress goes to stderr; the grouped result goes to stdout.
10. **Memory:** the aggregator streams per-host results. It keeps, per group, a hash, a bounded sample and a compressed host index list, never the full text of every host. Output of one host is fetched with bounded concurrency (8) and cut to the controller's 15 KiB first/last window.
11. **Exit code:** 0, 8 (some failed) or 9 (all failed) as in `02-commands.md` 3.10.5.

### 7.7 Follow and a running run
`machinarchy run r-4k2p9x1a --follow` shows the progress line and, for a single host (`--host`), streams that host's output as the controller exposes it (poll `.../output?from=N` while `live`). With several hosts it shows progress and, when the run ends, the grouped result; it does not interleave host output. `--wait-timeout 10m` stops watching after 10 minutes with exit 5 and the line `Still running. Watch again: machinarchy run r-... --follow`.

### 7.8 200 hosts, and what 500 and 5,000 mean
```
$ machinarchy run --on all -- uptime
Error: this would run on 500 hosts; one run can target at most 200.
Next:  narrow it, for example: machinarchy run --on tier=web -- uptime
```
The 200 limit is the controller's (`MaxOperationTargets`, C-05 proposes raising it). For a 200-host run the output is the same shape as 7.3-7.6; host lists compress to a few lines:

```
✔ 197 of 200 hosts succeeded
✔ app-[001-087,089-142,144-200]   exit 0   (195 hosts)
    ok
✔ app-[088,143]   exit 0   (2 hosts)   different output
    ok (degraded)
✖ app-[198-200]  could not connect (unreachable)   (3 hosts)
```
The aggregator is specified and golden-tested for 500 and 5,000 synthetic hosts (`09-acceptance-tests.md` G-04, G-05) so the output stays one screen when the controller limit is raised. Against a real server those two cases also need C-05 and C-06 (a summary and paged targets), because the current API returns every target inside the operation.

## 8. Host keys

**First trust** is section 2.1. **A changed key** is the case where a host that trusted a key now presents another (`HostKeyChanged`). It is shown as an alarm, not as a routine approval:

```
$ machinarchy hosts show web-01
web-01   ✖ key changed
  Trusted:   SHA256:Qm3vL0xk...
  Presented: SHA256:Zt9aP4rW...  (first seen 2026-11-26 09:41)
  The machine now presents a different SSH key. This is normal after a reinstall.
  It is also what a machine pretending to be web-01 would look like.

  Check with whoever runs web-01, then:  machinarchy hosts trust web-01 --replace
```
```
$ machinarchy hosts trust web-01 --replace
[company · production]  Replace the trusted key of web-01
  Old   SHA256:Qm3vL0xk...
  New   SHA256:Zt9aP4rW...
  Did you confirm the new key with whoever runs web-01, by a channel other than Machinarchy?
Type the first 8 characters of the NEW key (after SHA256:) : Zt9aP4rW
Type "web-01" to confirm: web-01
✔ web-01 now trusts the new key. Commands to it will be accepted again.
```
Differences from first trust: two typed confirmations, the old key is shown, a protected env also asks for the env name, and `--yes` and `--all-pending` are refused for a replacement. Non-interactive: `--replace --fingerprint SHA256:... --confirm web-01` (plus `--confirm-env` in a protected env).

## 9. Ctrl+C, cancel, retry, and "did it go through?"

Three different things must never be confused. This is what each does and what the **controller** guarantees; nothing more is promised.

| You do | The CLI | The controller guarantees | It does **not** guarantee |
|---|---|---|---|
| **Ctrl+C while watching** | stops watching, prints how to resume, exits 130 | The run was accepted into a durable queue and workers execute it independently of any client (`ADR-033`); a restart of workers or controller loses nothing; detached commands keep running under their supervisor on the host. | Anything about output you did not see; a detached command keeps only the first and last 15 KiB per stream. |
| **`run ID --cancel`** | asks the controller to cancel; shows `CancelRequested`, then the final state when it arrives | The request is recorded (`CancelRequested`); workers send a cancel to running targets; on SSH hosts a supervisor stops the process (TERM, then KILL after 10 s; under systemd the whole cgroup); on agent hosts the agent reports the final state. | That remote work stopped (`ADR-030`: cancellation closes local I/O without asserting that remote work stopped). Under the `setsid` supervisor, double-forked processes survive. A host that stays unreachable 5 minutes after cancel ends `Lost (unreachable_during_cancel)`. |
| **Terminate remote execution** | has no such command | - | - |

```
$ machinarchy run r-4k2p9x1a --follow
████████░░░░░░░░ 120/200  ✔ 112  ✖ 3  ● 85 running
^C
Stopped watching. The run keeps going on the hosts.
  Watch again:  machinarchy run r-4k2p9x1a --follow
  Cancel it:    machinarchy run r-4k2p9x1a --cancel
```
Exit 130. A second Ctrl+C exits at once (as today, `cmd/machinarchy/main.go:24`).

```
$ machinarchy run r-4k2p9x1a --cancel
[company · production]  Cancel run r-4k2p9x1a (85 hosts still running)
Cancel it? [y/N] y
Cancellation requested. The hosts have not confirmed yet.
████████████████ 200/200  ✔ 112  ✖ 3  ⏹ 80 cancelled  ? 5 outcome unknown
Run cancelled.
  ⚠ 5 hosts could not be reached while cancelling; the command may still be running there.
```
Exit 9 if no host succeeded, 8 otherwise. "cancelled" means the controller or supervisor reported it; it does not mean "nothing ran" (some hosts finished before the cancel arrived).

**Ctrl+C during a submit** (between "Run it? y" and the answer) is ambiguous because the controller has no idempotency key (C-12):
```
^C
Interrupted while sending the run. It may or may not have been created.
  Check:  machinarchy run
```
The same message appears when the connection drops or times out at that moment. The CLI never resubmits by itself.

**Retry-failed**
```
$ machinarchy run r-4k2p9x1a --retry-failed
[company · production]  Run again on 3 hosts: web-[09,13-14]
  Command   systemctl is-active nginx    (same as r-4k2p9x1a)
  Skipped   2 hosts with unknown outcome: web-[05,11]   (the command may already have run there)
            add --include-unknown to include them
Run it? [y/N] y
Run r-7c0a5e2d
...
```
It is a new run with a new ID; the old run is not changed. The CLI says "again" and never "fix". Hosts whose outcome is unknown or cancelled are not retried unless asked, because retrying a command that may already have run is the user's decision, not the CLI's.

## 10. Help, errors, "did you mean"

- `machinarchy --help` shows the four groups of section 1 of `02-commands.md`, then `Run 'machinarchy COMMAND --help' for details.`
- **Every** help screen ends with `Examples:` that are runnable as written (acceptance test U-02 greps for it).
- Unknown command or flag: the closest match by edit distance, at any depth:
```
$ machinarchy host add web-01
Error: unknown command "host" for "machinarchy".
Did you mean:  machinarchy hosts add web-01
```
- Old commands: `machinarchy get hosts` still works and prints on stderr `Deprecated: use "machinarchy hosts"` (`08-migration.md`).
- Errors use the four-part form of `02-commands.md` 2.3. Examples:
```
Error: web-09 is not ready (cannot connect: connection timed out).
Why:   the controller could not reach 10.0.0.9:22.
Next:  check the address and firewall, then: machinarchy hosts show web-09
```
```
Error: you are signed in with a reader token and cannot run commands.
Next:  use a token with the operator role: machinarchy tokens create NAME --role operator
```
```
Error: this server speaks API version 3; this CLI supports 1-2.
Next:  update the CLI: <release page>
```
(The last one needs C-11; until then the CLI can only notice that responses do not decode and says "The server answered in a way this CLI does not understand. Update the CLI, or check the address.")

## 11. Tab completion

Like git: `machinarchy h<TAB>` completes to `hosts`; with more than one match the shell shows a list to choose from (how the list looks, a menu or a row of words, is the shell's own behaviour: zsh and fish show a selectable menu, bash lists the words).

```
$ machinarchy <TAB><TAB>
access   admin   envs   hosts   login   logout   run   switch   tokens   whoami

$ machinarchy hosts s<TAB>
show

$ machinarchy hosts show we<TAB>
web-01  (ready)       web-02  (ready)       web-14  (waiting for key approval)

$ machinarchy run --on t<TAB>
tier=   tag-keys come from your hosts

$ machinarchy run --on tier=<TAB>
tier=db   tier=web

$ machinarchy run r-<TAB>
r-4k2p9x1a  uptime ✔ 14 ok        r-8d1q0b7c  systemctl is-active nginx ⚠ 11 ok, 3 failed
```
Descriptions appear in shells that support them (zsh, fish). Candidates and descriptions are plain text without colour.

**Installing it.** The first time `login` succeeds on a terminal, one extra line is printed (once per computer, remembered in the config):
```
  Tab completion:  machinarchy completion install
```
```
$ machinarchy completion install
Shell: zsh
This will write:   ~/.zsh/completions/_machinarchy
zsh must look in that folder. It already does (it is on your fpath).
Install? [y/N] y
✔ Installed. Open a new terminal, then try:  machinarchy h<TAB>
```
If zsh does not look there, nothing is written to `~/.zshrc`; the command prints the two lines to add and where:
```
Add these two lines to ~/.zshrc, then open a new terminal:
  fpath=(~/.zsh/completions $fpath)
  autoload -Uz compinit && compinit
```
When the CLI cannot reach the server or you are signed out, Tab still completes commands and flags; it simply offers no host names, and prints nothing.
